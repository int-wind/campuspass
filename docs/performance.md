# 压测方案与结果记录

## 固定数据与环境

- 数据：脚本生成 10,000 个合成账号、100 场活动；第 1 场 1,000 个名额，不含任何真实学生信息。
- 依赖：Docker Compose 中固定 MySQL 8.0.41、Redis 7.2.7、RabbitMQ 4.1.0；端口仅映射 localhost。
- 资源：MySQL CPU 2 核/内存 3 GiB，Redis 1 核/768 MiB，RabbitMQ 1.5 核/1 GiB；记录宿主机 CPU/内存、Docker 版本、Java 参数、JMeter 版本及镜像 digest。
- 两组共用相同数据、限流值、JMeter 版本、机器和依赖资源：基线 `ENROLLMENT_ASYNC=false`、`LOCAL_CACHE_ENABLED=false`；优化版两项均启用。
- JMeter 正式阶梯并发 20、50、100；每档 ramp-up 1 分钟、总时长 4 分钟（约 3 分钟稳态）、重复 3 次。200 并发只做连接池资源诊断，500 并发未纳入正式比较。
- 稳定后持续负载至少 30 分钟。保存原始 JTL、JMeter HTML、启动参数、环境配置和数据库对账结果。

本次可用验证环境：Windows 11 Pro，16 个逻辑 CPU，约 32 GiB RAM，Docker Desktop 29.5.3，Java 21.0.3，Maven 3.9.9，JMeter 5.6.3。真实依赖镜像：MySQL `8.0.41` (`sha256:bf577825b52ab281d6281fb281eabbfdc73507eda8f2c2745790251533ef0306`)、Redis `7.2.7-alpine` (`sha256:ddd16a9b1575a774c7e62956be8daa1de5b32cfb5c25b7a216aefed8e0919f9b`)、RabbitMQ `4.1.0-management` (`sha256:935b3f84c1e4a4ce45d211627f00030fa6721350efb52e0a6ed6924adedc68b7`)。

## 指标口径

- API 受理 P95：只统计报名入口响应，单独报告 202、429、409、5xx 数量。
- 报名完成延迟：从申请到数据库状态变为 `PENDING_CONFIRM` 或 `WAITLISTED`，不以 202 快速返回作为完成。
- 成功落库吞吐：每秒进入 `PENDING_CONFIRM` / `WAITLISTED` 的唯一请求数；另单列实际获得名额数，排除快速满员/限流造成的假提升。
- 活动详情 P95/P99、Redis 命中、SQL 查询次数、Outbox 延迟、RabbitMQ ready/unacked 积压、CPU/内存。
- 正确性：占用数不超过 capacity、每个用户/活动最多一条有效报名、核销状态只成功转换一次、容量流水余额与 `occupied_count` 一致。

## 正式阶梯压测结果

测试日期：2026-10-21。每档两组均使用 10,000 合成账号、100 场合成活动、同一 1,000 名额热点场次；每轮前停止应用、清空项目 RabbitMQ 队列并重建数据。基线配置 `ENROLLMENT_ASYNC=false`、`LOCAL_CACHE_ENABLED=false`；优化配置两项均为 `true`。两组固定 `LOGIN_IP_LIMIT=10000`、`SENTINEL_EVENT_DETAIL_QPS=5000`、`DB_POOL_SIZE=20`、JVM `-Xms512m -Xmx2g`。每档 20/50/100 线程各重复 3 次，JMeter 时长 240 秒，其中 ramp-up 60 秒；保存的 JTL 包含 HTTP 样本和两个 JMeter 内部脚本样本，以下吞吐仅从 4 个 HTTP 标签计算，避免把内部样本算成 API 请求。

### 30 分钟持续负载

真实优化配置下运行 20 个 JMeter 线程，ramp-up 60 秒、测量 30 分钟（总时长 1,860 秒），测试用 Access Token TTL 单独设为 45 分钟以覆盖全窗口；循环 pacing 设为 500ms，避免测试机在 10,000 个唯一账号处理完后空转。JTL 位于 `reports/soak/20261021_0345_retry/results.jtl`，HTML 位于同目录 `html/`。

- JTL 总样本 62,774；4 个 HTTP 标签共 41,382 个样本：登录 10,000、报名申请 10,000、最终状态查询 10,003、活动详情 11,379；HTTP 失败 0。
- 热点场次最终容量 1,000、`occupied_count=1,000`、占用状态报名行 1,000、候补 3,000、持久化报名请求 10,000；该场请求终态为 `PENDING_CONFIRM=1,000`、`WAITLISTED=3,000`、`EXPIRED=6,000`。容量流水余额为 1,000。`scripts/check-invariants.sql` 执行无违规行，含超额、活动容量流水不平及重复有效报名检查。
- 结束时 RabbitMQ 报名队列 ready/unacked 为 0/0、消费者 1；死信队列 0；TTL 延迟队列 998（与尚在确认窗口的记录同量级）。应用健康端点返回 `UP`。
- 结束附近一次 `docker stats` 快照：MySQL 15.78% CPU、668.7 MiB；Redis 0.54%、197.1 MiB；RabbitMQ 1.91%、109.9 MiB。此为瞬时值而非峰值。宿主 Docker 同时运行非本项目的 Kubernetes 和 Nacos 容器，宿主 CPU 不是完全隔离的测试条件。

复现 soak 的 JMeter 命令（先运行 `prepare-benchmark.ps1`、以优化模式启动应用并取新的热点活动 ID）：

```powershell
jmeter.bat -n -t 'perf/campuspass-load.jmx' '-Jthreads=20' '-JtotalUsers=10000' '-Jramp=60' '-Jduration=1860' '-JthinkTime=500' "-JeventId=$eventId" "-Jjtl=reports/soak/<run>/results.jtl"
jmeter.bat -g 'reports/soak/<run>/results.jtl' -o 'reports/soak/<run>/html'
```

首次持续测试在未设置 pacing 时因 JMeter 账号分配完后进入空转，约 8 分 54 秒后客户端临时端口耗尽、错误率升至约 37%；原始诊断文件留在 `reports/soak/20261021_0332/results.jtl`，不计入上述结果。修正为可配置循环 pacing 后重新完成完整测试。正式四分钟对照使用 `thinkTime=0`；持续测试使用 500ms。

### 范围和限制

- 200 并发连接池诊断在 `DB_POOL_SIZE=20` 时约 0.20% 错误；调到 50 后仍约 0.09% JDBC 获取连接超时。故 20/50/100 是本机正式稳定档，200/500 不进入比较。
- 当前 JTL 尚未关联每个申请的 requestId 与最终数据库终态，且没有采集 SQL 回源次数、Caffeine/Redis 命中率及每个请求的端到端“申请→持久化完成”延迟；这些指标不作推测。
- 集成测试覆盖 6 用户并发争抢 1 个名额（最终 1 个待确认、5 个候补且队列位置连续）、同一幂等键重复请求、重复 RabbitMQ 消息、确认/取消竞争、候补递补、核销及重复核销、角色限制、Refresh Token 并发单成功及 Redis TTL 过期、注销撤销 Access Token；单元测试覆盖 Access Token 过期。另用真实依赖验证 RabbitMQ 重启后的 Outbox 重投、Redis 重启期间持久请求恢复、消费者进程强制终止后的 RabbitMQ 消息重投，以及 MySQL 写入失败后的预占租约释放和解除故障后的重新报名。详见 [`docs/recovery.md`](recovery.md)；这些本机故障验证不等价于生产混沌测试。
- 所有账号和活动均为本地合成数据，不代表真实学校用户流量；结果只适用于本机单实例与上述资源配置。
